Deploy en Vercel vs GitHub Pages: ¿cuándo uso cada uno y cuándo ambos?

Ambos son gratuitos, pero no son lo mismo. Esto es lo que considero antes de elegir.

3 min de lectura Leer →

La mayoría de mis proyectos terminan en uno de los dos. Con el tiempo fui desarrollando un criterio claro para elegir.

GitHub Pages

Ideal para proyectos estáticos simples: portafolios, landing pages, demos de HTML/CSS/JS puro. Cero configuración si el repo es público.

Vercel

Cuando el proyecto tiene; dominio propio, React, variables de entorno, o necesito features como redirects y edge functions.

GitHub y Vercel juntos

La tercera opción, y la que uso en la actualidad, es subir el repositorio a GitHub y desplegar el proyecto en Vercel.

La razón técnica concreta: Vercel entiende frameworks como React, Next.js o Vite, hace el npm run build por vos, sirve los archivos estáticos optimizados, y te da CDN global, HTTPS y dominio custom sin configurar nada. GitHub Pages no tiene ese pipeline de build integrado.

En una línea: GitHub = repositorio, Vercel = servidor inteligente que escucha ese repositorio.

CSS que escribo diferente desde que aprendí custom properties

Las variables CSS no son solo conveniencia: cambian la forma en que pensás el diseño de un sistema.

4 min de lectura Leer →

Antes de usar custom properties en serio, mi CSS era un cementerio de valores hardcodeados repetidos. Un color cambiaba y tenía que hacer find & replace por todo el proyecto.

¿Qué cambió?

Empecé a definir todas mis variables en :root y a pensar en el CSS como un sistema de tokens. Colores, espaciados, tipografías, tiempos de animación. Todo centralizado.

  • Un cambio en :root impacta todo el sitio al instante.
  • Podés tener temas (dark/light) con solo sobrescribir variables.
  • Tu CSS se vuelve autodocumentado.

El salto de calidad es real. Cuando un cliente te pide cambiar la paleta de colores a último momento, tener todo en :root te salva la vida 😅. Si todavía no lo hacés en todos tus proyectos, te recomiendo que empieces hoy.

Lo que aprendí enseñando, es que todavía estaba aprendiendo

Ser instructor antes de sentirte "listo" es incómodo. También es lo mejor que me pasó profesionalmente.

5 min de lectura Leer →

Cuando empecé a dar clases en el Instituto CEA, todavía estaba consolidando muchos de los conceptos que enseñaba. Eso generaba una tensión constante.

La trampa de esperar estar listo

Nadie se siente completamente listo para enseñar y el sindrome del inspostor siempre está latente. Explicar flexbox, grid o integraciones a personas con distintos niveles técnicos te obliga a entenderlo desde múltiples ángulos. Creo que eso te hace mejor desarrollador, no solo mejor docente.

18 Feb 2026 Tips

3 hábitos que mejoraron mi velocidad de desarrollo

No son frameworks ni herramientas nuevas. Son cambios pequeños que se acumulan.

3 min de lectura Leer →

Después de meses trabajando en proyectos propios y freelance, noté que la diferencia de velocidad no vino de aprender una tecnología nueva sino de estos tres cambios:

1. Snippets para todo lo que repito

Estructura HTML base, componentes comunes, funciones de utilidad. Si lo escribí más de dos veces, lo convierto en snippet en VS Code.

2. Commits pequeños y descriptivos

Un commit por feature o fix. Nada de "cambios varios". Cuando tengo que revertir algo, me agradezco a mí mismo.

3. Diseñar en el browser, no solo en Figma

Para proyectos chicos, empiezo directo en CSS. Itero más rápido y el resultado final ya está en código.

Cómo mejoré el rendimiento del sitio web de un cliente optimizando su puntuación en Google Core Web Vitals

De un 65% a un 97% en Google Core Web Vitals

7 min de lectura Leer →

Recientemente trabajé en la optimización del rendimiento de un sitio web con el objetivo de mejorar su puntuación en Google Core Web Vitals. Aunque el sitio ya tenía buenos resultados en escritorio, el rendimiento en dispositivos móviles todavía tenía margen de mejora. Para medir cada avance utilicé herramientas como Google PageSpeed Insights y Lighthouse, monitoreando el impacto de cada cambio antes de continuar con la siguiente optimización.

¿Qué problemas encontré?

El análisis inicial reveló varios factores que estaban afectando la velocidad de carga y la experiencia del usuario:

  • Recursos JavaScript que bloqueaban el renderizado inicial.
  • Imágenes que podían optimizarse aún más.
  • Fuentes externas que agregaban solicitudes adicionales.
  • Recursos incluidos dentro de la ruta crítica de renderizado.
  • Configuraciones de seguridad que interferían con algunas herramientas de análisis.

¿Qué optimizaciones implementé?

La estrategia consistió en aplicar mejoras progresivas y medir el resultado de cada una. Entre las acciones realizadas se incluyeron:

  • Optimización de la carga de archivos JavaScript para evitar bloqueos innecesarios.
  • Reducción del peso de imágenes mediante formatos modernos y compresión inteligente.
  • Revisión de los recursos críticos que participan en la carga inicial de la página.
  • Ajustes en la configuración de seguridad para garantizar el correcto funcionamiento de las herramientas de analítica.
  • Validación constante mediante auditorías de rendimiento.

¿Cómo medí los resultados?

Cada modificación fue monitoreada utilizando Google PageSpeed Insights y Lighthouse. Este enfoque permitió identificar cuáles cambios generaban mejoras reales y cuáles tenían un impacto menor. En lugar de aplicar múltiples modificaciones simultáneamente, cada optimización fue evaluada individualmente para obtener resultados medibles y confiables.

Resultados obtenidos

Luego de las optimizaciones, la puntuación móvil mejoró significativamente respecto al estado inicial, mientras que el rendimiento en escritorio se mantuvo en niveles muy altos. Además de la mejora numérica en las herramientas de auditoría, se consiguió una carga más rápida del contenido principal y una mejor experiencia para los usuarios.

  • Mejora de la puntuación de rendimiento móvil.
  • Reducción de recursos bloqueantes.
  • Optimización de imágenes y tiempos de carga.
  • Mejor experiencia de navegación para los visitantes.
  • Validación continua mediante Google Core Web Vitals.

Una de las conclusiones más importantes de este proyecto fue comprobar que no siempre es necesario reconstruir un sitio completo para obtener mejoras importantes. Muchas veces, pequeñas optimizaciones bien ejecutadas y respaldadas por métricas pueden generar un impacto significativo tanto en la experiencia del usuario como en el rendimiento general del sitio.

Cómo resolví conflictos entre Content Security Policy y Google AdSense

Implementar una CSP mejoró la seguridad del sitio, pero también bloqueó recursos necesarios para Google AdSense. Así fue el proceso para encontrar el equilibrio entre protección y funcionalidad.

4 min de lectura Leer →

Cuando decidí implementar una Content Security Policy (CSP), el objetivo era reforzar la seguridad del proyecto limitando qué recursos externos podían ejecutarse en el navegador.

La teoría era simple: permitir únicamente los dominios necesarios y bloquear cualquier origen desconocido. Sin embargo, al integrar Google AdSense comenzaron a aparecer errores que impedían el funcionamiento correcto de algunos servicios de Google.

El problema

Después de desplegar la nueva política de seguridad, la consola del navegador empezó a mostrar bloqueos relacionados con recursos de Google Ads.

Aunque AdSense estaba correctamente instalado, varias solicitudes eran rechazadas por las directivas definidas en la CSP, impidiendo la carga completa de algunos componentes.

El proceso de diagnóstico

En lugar de desactivar la política de seguridad, decidí revisar cada error individualmente para entender exactamente qué recurso estaba siendo bloqueado.

El proceso consistió en:

  • Revisar la consola del navegador.
  • Identificar el dominio bloqueado.
  • Determinar qué directiva de la CSP estaba provocando el rechazo.
  • Actualizar la configuración.
  • Volver a desplegar el proyecto.
  • Repetir el proceso hasta eliminar todos los errores.

Los bloqueos encontrados

Durante el análisis aparecieron distintos tipos de restricciones que afectaban el funcionamiento de AdSense.

Scripts: algunos archivos JavaScript utilizados por Google no estaban contemplados dentro de la directiva script-src.

Conexiones: ciertos servicios internos utilizados para validación y control de tráfico eran bloqueados por la directiva connect-src.

Iframes: varios componentes publicitarios requerían dominios adicionales dentro de frame-src para cargar correctamente.

Lo que aprendí

La principal conclusión fue que una CSP efectiva no se construye copiando configuraciones genéricas encontradas en Internet.

Cada proyecto utiliza servicios distintos y la política debe reflejar exactamente las dependencias reales de la aplicación.

También comprobé que una configuración demasiado restrictiva puede afectar funcionalidades legítimas, incluso cuando estas provienen de proveedores confiables como Google.

Resultado final

Después de varios ajustes logré mantener una política de seguridad activa sin afectar la monetización del sitio.

  • Google AdSense volvió a funcionar correctamente.
  • Desaparecieron los errores de consola.
  • La CSP continuó protegiendo el sitio.
  • Solo se habilitaron los dominios estrictamente necesarios para Analytics, Tag Manager y AdSense.

El resultado fue un equilibrio razonable entre seguridad, rendimiento y compatibilidad.

Conclusión

Muchas veces los errores de consola parecen simples advertencias, pero detrás de ellos puede haber funcionalidades completas que dejan de operar correctamente.

Resolver estos conflictos me permitió comprender mejor cómo interactúan las políticas de seguridad del navegador con servicios externos de monetización y análisis.

Más allá de solucionar un problema puntual, fue una experiencia útil para construir una configuración más sólida y mantenible para el proyecto.
